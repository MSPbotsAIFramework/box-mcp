## Product design

### Goals / Non-goals

**Goals (v1):**
- An AI agent connected through the Box connector can, for a Box enterprise the requester has
  Service Account access to: browse folders, read file/folder metadata, download file content
  (via a time-limited URL), upload new files, rename/move files and folders, delete files and
  folders (with explicit confirmation for deletes), search Box content by keyword, and create or
  inspect a shared link for a file or folder.
- Every action is attributable to the credentials supplied on that request (the connector does
  not store or share credentials across requests) and is logged by the surrounding MCP Gateway
  infrastructure (audit logging is a Gateway-level feature per `hudu-mcp`'s README "MSPbots
  Connector" section; this connector does not re-implement it).

**Non-goals (v1)** — none of these are named in the ticket; they are deferred to a future
iteration if a concrete need shows up:
- File versions / version history, trash / restore, comments, tasks, collaborations management,
  webhooks, retention policies, metadata templates, legal holds, classification.
- Acting as a specific Box end user (App User / "As-User" impersonation) — v1 only supports the
  Service Account (enterprise-wide) identity. See Open Questions.
- Files larger than 10 MB (v1 upload cap, see §4.3) — the chunked-upload API for files over
  Box's own 50 MB simple-upload ceiling is out of scope.

### Acceptance criteria

- **AC1**: Given valid Box Service Account credentials (Client ID, Client Secret, Enterprise ID)
  are supplied as request headers, When the agent calls `box_test_connection`, Then the tool
  returns `{"status":"ok","user":{"id","name","login"}}` for the authenticated Service Account.
- **AC2**: Given one or more required Box credential headers are missing, When any Box tool is
  called, Then the server returns HTTP 401 naming the missing header(s), and no call is made to
  Box's token endpoint or API.
- **AC3**: Given a valid Box folder id, When `box_get_folder_info` is called, Then the tool
  returns the folder's id, name, parent folder id, size, item count, and owner login.
- **AC4**: Given a Box folder containing files and subfolders, When `box_list_folder_items` is
  called, Then the tool returns a page of items (id, name, type) with `count`, `has_more`,
  `next_offset`; default page size is 25, hard cap 200.
- **AC5**: Given a parent folder id and a name, When `box_create_folder` is called, Then a new
  folder is created under that parent in Box and its id/name are returned.
- **AC6**: Given an existing Box folder, When `box_update_folder` is called with a new name
  and/or a new parent id, Then the folder's name/parent in Box reflect the change.
- **AC7**: Given an existing empty Box folder, When `box_delete_folder` is called, Then the
  folder is removed from Box. Given a non-empty folder, When `box_delete_folder` is called
  without `confirm: true` and `recursive: true`, Then nothing is deleted and the tool returns an
  `invalid_argument` error naming what is required.
- **AC8**: Given a valid Box file id, When `box_get_file_info` is called, Then the tool returns
  the file's id, name, size, parent folder id, and last-modified timestamp.
- **AC9**: Given a valid Box file id, When `box_get_file_download_url` is called, Then the tool
  returns a time-limited direct download URL for that file's content; the file content itself is
  never embedded in the tool's JSON response.
- **AC10**: Given text or base64-encoded content no larger than 10 MB and a target parent folder
  id, When `box_upload_file` is called, Then a new file is created in Box with that content and
  its id/name are returned. Given content larger than 10 MB, When `box_upload_file` is called,
  Then the tool rejects it with an `invalid_argument` error stating the size cap — it never
  silently truncates content.
- **AC11**: Given an existing Box file, When `box_update_file` is called with a new name and/or a
  new parent id, Then the file's name/parent in Box reflect the change.
- **AC12**: Given an existing Box file, When `box_delete_file` is called with `confirm: true`,
  Then the file is removed from Box. Given the same call without `confirm: true`, Then nothing is
  deleted and the tool returns an `invalid_argument` error.
- **AC13**: Given a search keyword, When `box_search` is called, Then the tool returns matching
  files/folders (id, name, type) from Box's search index, honoring the same `limit`/`offset`
  pagination contract as the list tools.
- **AC14**: Given an existing file or folder and an access level (`open` / `company` /
  `collaborators`), When `box_create_shared_link` is called, Then Box creates (or replaces) a
  shared link for that item and the tool returns the link URL and access level.
- **AC15**: Given an item, When `box_get_shared_link` is called, Then the tool returns the
  existing shared link URL and access level, or `{"shared_link": null}` if none exists.
- **AC16**: Given Box or the credential exchange returns an error (invalid credentials, item not
  found, rate limited, upstream 5xx), When any tool is called, Then the tool returns the
  structured error envelope `{"error":{"code","message","retryable"}}` with the matching `code`
  — it never raises an unhandled exception or leaks a raw Box response body containing the
  client secret.
- **AC17** (multi-tenant / isolation): Given two concurrent requests carry different Box
  credentials (different Box enterprises), When both call Box tools at the same time, Then each
  request's calls to Box use only that request's own credentials, and neither request's access
  token or data is observable from the other.

### Open questions

- [assumed] Should v1 support acting as a specific Box end user (App User / "As-User" header)
  instead of only the enterprise-wide Service Account? — Assumed **no**: the ticket names no
  per-user access requirement, the Service Account model matches how other MSP-admin-style
  connectors in this org work (enterprise-wide read/write under one set of credentials), and
  adding App User support later is an additive, non-breaking change (one more optional
  credential header). If this assumption is wrong, §4.3/§5 (credential fields) need a second
  header set added; nothing else in this design needs to be redone.
- [non-blocking] Exact current Box API rate limits per endpoint are not published as a single fixed
  number (`developer.box.com` describes limits as varying by endpoint/plan) — the design does not
  hardcode a request-per-second figure and instead backs off on HTTP 429 using the `Retry-After`
  response header (§7.2).

## Tech design

Stack: Python 3.12 + uv + FastMCP + httpx (matches `hudu-mcp`, the current standard for repos in
this org; `box-mcp` has no build files yet — this is the first commit of real code).

### Conclusion

Build a stateless FastMCP server wrapping Box's public REST API v2.0. Authenticate per request via
Box's Client Credentials Grant (Service Account) using credentials carried on three request
headers; never cache the exchanged access token across requests. Implement 14 tools across 4 areas
(connection, folders, files, search/sharing) that map Box REST endpoints to agent-sized operations,
following the `hudu-mcp` project shape (same middleware, error envelope, and pagination contract).

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| Cache the CCG access token across requests (keyed by client id) | Exchange once per ~55 min, reuse for all requests with that client id | Fewer calls to Box's token endpoint | Violates the SOP's "never cache a derived token across requests" isolation rule (§3.3/§3.4); a cache key collision or TTL bug would leak one tenant's token to another | **Rejected** |
| Exchange a fresh CCG token on every tool call | One extra HTTPS round-trip per request to `https://api.box.com/oauth2/token` | Matches the "truly stateless, per-request credentials" contract exactly; no shared mutable state | ~100–300 ms added latency per call | **Chosen** — correctness over the small latency cost; this is the same trade-off every other OAuth-token vendor in this org makes |
| Build on Box's official Python SDK (`box-sdk-gen`) | Use the vendor SDK for the HTTP calls | Less hand-written request code | Pulls in a large third-party SDK with its own auth/session model that assumes a long-lived client object — fights the "no state across requests" requirement and needs adapting; `hudu-mcp` and other repos in this org use a thin `httpx` client for the same reason | **Rejected**: thin `httpx` wrapper, consistent with the rest of the org's connectors (§3 reuse) |

No alternative was considered for "which Box auth grant to use" beyond CCG: Box's only
non-interactive, no-user-present server-to-server option is CCG (or legacy JWT, which Box's own
docs describe as available only "if your enterprise allows switching from CCG" — i.e. CCG is the
current default and the one to build against).

### Data & API contract

Credential headers (read by `src/box_mcp/auth.py`, declared in the README table):

| Header | Required | Type | Description |
|---|---|---|---|
| `X-Box-Client-Id` | Yes | string | Box app Client ID (Box Developer Console → App → Configuration) |
| `X-Box-Client-Secret` | Yes | password | Box app Client Secret (same page) |
| `X-Box-Enterprise-Id` | Yes | string | Box Enterprise ID the Service Account authenticates as |

Token exchange (per request, not cached):

```
POST https://api.box.com/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id={X-Box-Client-Id}&client_secret={X-Box-Client-Secret}
&box_subject_type=enterprise&box_subject_id={X-Box-Enterprise-Id}

-> 200 {"access_token": "...", "expires_in": 3599, "token_type": "bearer"}
-> 400/401 on invalid credentials -> mapped to {"error":{"code":"unauthorized", ...}}
```

Representative tool-to-endpoint mapping (full field lists in the README once written; all calls
use `Authorization: Bearer {access_token}` from the exchange above):

| Tool | Box REST call |
|---|---|
| `box_test_connection` | `GET https://api.box.com/2.0/users/me` |
| `box_get_folder_info` | `GET /2.0/folders/{folder_id}` |
| `box_list_folder_items` | `GET /2.0/folders/{folder_id}/items?limit=&offset=` |
| `box_create_folder` | `POST /2.0/folders` `{"name","parent":{"id"}}` |
| `box_update_folder` | `PUT /2.0/folders/{folder_id}` `{"name"?,"parent":{"id"}?}` |
| `box_delete_folder` | `DELETE /2.0/folders/{folder_id}?recursive=` |
| `box_get_file_info` | `GET /2.0/files/{file_id}` |
| `box_get_file_download_url` | `GET /2.0/files/{file_id}/content` (not following the redirect; the `Location` header is the time-limited URL returned to the agent) |
| `box_upload_file` | `POST https://upload.box.com/api/2.0/files/content` (multipart, `attributes` + file part) |
| `box_update_file` | `PUT /2.0/files/{file_id}` `{"name"?,"parent":{"id"}?}` |
| `box_delete_file` | `DELETE /2.0/files/{file_id}` |
| `box_search` | `GET /2.0/search?query=&limit=&offset=` |
| `box_create_shared_link` | `PUT /2.0/files\|folders/{id}` `{"shared_link":{"access":...}}` |
| `box_get_shared_link` | `GET /2.0/files\|folders/{id}?fields=shared_link` |

Example tool response (`box_get_folder_info`):

```json
{"id":"12345","name":"Client Reports","parent_id":"0","size":48213991,
 "item_count":37,"owner_login":"service-account@enterprise.box.com"}
```

Example error envelope (shared shape across all tools, matching `hudu-mcp`):

```json
{"error":{"code":"not_found","message":"Box returned HTTP 404 for folder 12345: not found","retryable":false}}
```

DB: none — this service has no database.

Backward compatibility: not applicable — first version of a new connector, no existing tenants
registered against it yet.

### Key flow / sequence

```
Agent -> Gateway -> POST /mcp (tool call, Box credential headers) -> box-mcp
  box-mcp: middleware reads 3 headers; 401 if any missing
  box-mcp -> POST api.box.com/oauth2/token (client_credentials) -> access_token
  box-mcp -> Box REST call for the tool (Authorization: Bearer access_token)
  box-mcp -> maps Box response/error -> tool JSON result or error envelope
  box-mcp: access_token discarded at end of request (ContextVar reset in finally)
```

### Non-functional

- **Idempotency / concurrency**: read tools are naturally idempotent. `box_create_folder` /
  `box_upload_file` are not idempotent (Box assigns a new id per call); this matches Box's own API
  and is called out in the tool description so an agent does not assume safe retries. No local
  state is held between requests (AC17), so concurrent requests from different tenants cannot
  interfere with each other.
- **Performance**: list/search responses capped at `limit<=200` and the service's own 20000-char
  response-size cap (SOP §2), with `has_more`/`next_offset` for continuation, matching
  `hudu-mcp`'s contract. Outbound timeouts 5 s connect / 30 s read; a single tool call (including
  the token exchange) stays under 120 s even with retries.
- **Security**: credentials arrive only on request headers, are held only in a `ContextVar` for
  the lifetime of the request, and are never written to logs, disk, or the exchanged-token cache
  (there is no such cache — see Option analysis). The client secret is never echoed back in any
  tool response or error message (error envelopes carry Box's error text, not the request
  credentials). Delete tools require explicit `confirm: true` (AC7, AC12).
- **Multi-tenant isolation**: each request's Box Enterprise ID is whatever came in on that
  request's headers; nothing is cached or shared across requests, so one tenant's Box content is
  never reachable using another tenant's request path (AC17, tested in
  `tests/test_middleware.py`).
- **Observability**: structured logs include `tool_name`, Box HTTP status, and the mapped error
  `code`, but never header values or the raw request/response body (which could carry file
  content or the client secret).

### Rollout & rollback

- No feature flag — this is a new, previously-nonexistent connector; nothing is being changed for
  existing users. Rollout is: merge to `main` → first-version `/api/vendor-register` call (new
  vendor, not yet known to the INT gateway) → connector becomes available to authorize in the
  Agent Platform.
- Rollback: if a defect is found after INT registration, a fix follows the normal `dev/<ticket>` →

### Risks & dependencies

- **Risk**: Box's CCG token endpoint adds one network round-trip to every tool call. Mitigated by
  keeping the request-level cost visible in the design (Option analysis) rather than working
  around it with a cache that would violate the isolation requirement.
- **Risk**: field names in the representative contract above (§5) are drawn from Box's public
  reference docs read during design, not from a live call (no Box test account available) — the
  dev leg must verify against a real response or the OpenAPI spec and adjust field names if they
  differ; this does not change the tool list or the overall shape.
- **Dependency**: none on other open tickets or unmerged platform changes. Depends only on the
  publicly available `https://developer.box.com/reference/` and Box's enterprise CCG setup
  (Client ID/Secret/Enterprise ID), which are the requester's/customer's own Box admin
  configuration, not something this ticket provisions.
- **Decisions made by DEV01** (SOP §A4, no one to ask during an unattended design tick):
  - Chose Service Account (Enterprise ID) over App User (per-user impersonation) for v1 —
    simpler credential contract (3 headers, not 4+), matches the enterprise-wide-admin pattern
    used elsewhere in this org; alternative (App User) deferred, see Open Questions.
  - Chose to exchange a fresh CCG token per request rather than caching it — correctness
    (isolation) over latency; alternative (cached token) rejected, see Option analysis.
  - Chose a 10 MB v1 upload cap, well under Box's own 50 MB simple-upload ceiling — base64-encoding
    a 50 MB file into a single MCP tool call is impractical for an LLM-driven caller; alternative
    (support the full 50 MB, or implement Box's chunked-upload API for larger files) deferred to a
    future iteration if a concrete need for larger files appears.
  - Picked 14 tools (not more) covering browse/read/create/update/delete/search/share; left out
    comments, tasks, collaborations, webhooks, versions, trash/restore, retention/legal-hold,
    metadata templates — none are named in the ticket, and Box's own tool surface for these would
    roughly double the tool count past the SOP's practical guidance to keep services focused.
